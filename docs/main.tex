\title{\ToolRobustBench: Stage-Wise Perturbation Evaluation and Failure Diagnosis for Tool-Calling Agents}

\author{Anonymous ACL submission}

\begin{document}

\begin{abstract}
Large language models (LLMs) rely on tool calling as a fundamental agent capability, enabling them to invoke external systems and complete tasks beyond text generation. However, clean end-to-end (E2E) success cannot identify where a tool-use failure originates or how it propagates through a call. We introduce \ToolRobustBench, a stage-wise diagnostic benchmark for tool-calling agents, where an agent selects a tool, supplies structured arguments, and interprets the returned feedback. \ToolRobustBench aligns four perturbation families with the tool-use pipeline: tool-interface, user-intent, tool-output/observation, and runtime-environment perturbations. It attributes failures to tool selection, schema grounding, argument binding, tool-output/runtime-feedback handling, and E2E task success. Experiments on 15,456 single-family instances across 7 models, 16 sampled local tools, 4 perturbation families, and 14 subtypes show strong clean performance and substantial robustness degradation, with tool-output/observation perturbations forming the dominant bottleneck across models. Exactly matched mixed-family experiments show that isolated constituent averages consistently overestimate combined robustness. Thus, \ToolRobustBench provides a deterministic and cascade-aware benchmark for diagnosing robustness beyond clean tool-calling accuracy; the anonymized artifact is available at \url{https://anonymous.4open.science/r/toolrobustbench/}.
\end{abstract}

\section{Introduction}

Large language models (LLMs) increasingly act as \emph{tool-calling agents}: systems that infer user intent, select an external tool, bind structured arguments, and interpret returned evidence or runtime feedback. Each stage can fail under deployment shifts such as opaque tool names, overlapping descriptions, indirect requests, missing evidence, or runtime faults. Clean end-to-end success cannot reveal whether these disruptions are handled reliably or where a failed call first departs from the intended process.

Existing benchmarks cover large-scale tool use and stable application programming interface (API) execution \citep{qin2024toolllm,guo2024stabletoolbench}, as well as interactive trajectories and noisy tool-use conditions \citep{lu2025toolsandbox,wang2026agentnoisebench}. They do not localize the first failed stage under controlled perturbations.

A failed call has both a symptom and a source: an incorrect argument may follow from tool-selection confusion, and a runtime symptom may originate in upstream argument corruption. \ToolRobustBench{} addresses this gap through controlled single-call evaluation with stage-aligned perturbations and deterministic cascade backtracking.

Our contributions are:

\begin{enumerate}
    \item A four-family, stage-aligned perturbation taxonomy and deterministic cascade-aware attribution that separates final symptoms from primary sources and yields stage-specific repair targets.
    \item A reproducible 40-tool local environment with stable gold calls, outputs, runtime states, and diagnostic targets.
    \item A large-scale evaluation of seven models on 15,456 single-family instances, producing a reproducible robustness leaderboard and identifying tool-output/observation handling as the shared cross-model bottleneck.
    \item An exactly matched mixed-family analysis showing that isolated constituent averages overestimate combined robustness, while localized positive contrasts arise when added conflict or runtime cues make failures more salient.
\end{enumerate}

\section{Related Work}

\noindent\textbf{Language-model evaluation.}
General benchmarks such as Massive Multitask Language Understanding (MMLU; \citealp{hendrycks2021mmlu}), Beyond the Imitation Game benchmark (BIG-bench; \citealp{srivastava2023bigbench}), and Holistic Evaluation of Language Models (HELM; \citealp{liang2023helm}) established broad capability and evaluation-protocol foundations; \citet{chang2024survey} synthesize this rapidly expanding landscape. Tool-mediated action adds a process-level requirement: two systems with the same end-to-end success rate may fail at different stages and therefore require different corrections.

\noindent\textbf{Tool calling and agent processes.}
API-Bank \citep{li2023apibank} and ToolBench \citep{qin2024toolllm} extend evaluation to API retrieval, tool selection, and argument binding. Gorilla \citep{patil2024gorilla} evaluates selection and invocation in large API collections, ToolAlpaca \citep{tang2023toolalpaca} studies generalization to unseen tools, and the Berkeley Function Calling Leaderboard (BFCL; \citealp{patil2025bfcl}) covers serial, parallel, and agentic function calling. StableToolBench \citep{guo2024stabletoolbench} motivates stable simulated APIs. AgentBench \citep{liu2024agentbench}, WebArena \citep{zhou2024webarena}, ToolSandbox \citep{lu2025toolsandbox}, and $\tau$-bench \citep{yao2025taubench} emphasize stateful environments and trajectories. \ToolRobustBench{} uses deterministic single-call tasks to isolate observation recovery and runtime-state judgment.

\noindent\textbf{Robustness and failure attribution.}
AgentNoiseBench \citep{wang2026agentnoisebench} studies realistic solvability-preserving user/tool noise, while RoTBench \citep{ye2024rotbench} studies multi-level tool-learning robustness. Who\&When \citep{zhang2025whowhen} attributes failures across agents and trajectory steps, whereas AgentHarm \citep{andriushchenko2025agentharm} evaluates harmful multi-step behavior. \ToolRobustBench{} localizes controlled perturbation entry points and cascade-aware failure sources within one call. Table~\ref{tab:related-comparison} makes these protocol differences explicit.

\section{Design of \ToolRobustBench}

\subsection{Task Formulation}
\label{sec:task-formulation}

Let $x$ denote a user request and let $\mathcal{R}=\{t_1,\ldots,t_n\}$ denote its candidate tool registry. Each \ToolRobustBench{} instance is represented by the tuple
\begin{equation}
I=(x,\mathcal{R},t^*,a^*,o^*,y^*,p),
\end{equation}
where each tool $t\in\mathcal{R}$ exposes a name, a natural-language description, a JavaScript Object Notation (JSON) schema, a deterministic executor, and an output format. The remaining tuple elements are the intended tool $t^*$, structured argument object $a^*$, deterministic tool output $o^*$, expected final result $y^*$, and perturbation specification $p$ (family, subtype, and severity). A \emph{source anchor} is a clean request--tool--argument--output instance from which perturbed variants are derived.

In pre-execution settings---clean, tool-interface, and user-intent---the model outputs a structured tool call $\hat{c}=(\hat{t},\hat{a})$. The scorer checks the selected tool, schema validity, bound arguments, and the result obtained by deterministic execution. In post-execution settings---tool-output/observation and runtime-environment---the model first completes the initial tool call and then, after receiving perturbed returned evidence or runtime feedback, outputs an observation-recovery or post-execution decision. These settings therefore evaluate not only selection and binding, but also interpretation of noisy evidence and execution-state feedback.

For C/D families, the model uses the original request, selected tool, available clean context, and perturbed returned evidence or runtime feedback to recover the final decision within the complete tool-calling episode.

At the instance level, success is binary: $s_i=1$ when the model selects $t^*$, produces a schema-valid argument object matching $a^*$, obtains the expected executed output where execution is applicable, and returns the expected final result $y^*$; otherwise $s_i=0$. For runtime-environment instances, success additionally requires the predicted runtime fields defined in Section~\ref{sec:taxonomy}---status, retryability, failure type, and final result---to agree with their gold targets whenever those judgments apply. Aggregate robustness metrics are defined separately below.

The diagnostic objective is not only to determine whether a tool call succeeds, but also to identify the earliest stage at which the model departs from the intended tool-use process. Accordingly, each evaluated record preserves the observed error label, primary error label, earliest failed stage, error source stage, cascade indicator, and boundary-violation indicator. To operationalize this diagnostic objective, we decompose each tool call into five capability axes, described next.

\subsection{Tool-Calling Capability Axes}

\ToolRobustBench{} uses five axes: S1 tool selection, S2 schema grounding, S3 argument binding, S4 tool-output/runtime-feedback handling, and S5 end-to-end success. These axes locate the earliest source stage; Table~\ref{tab:stages} summarizes their targets and typical failures.

\subsection{Stage-Aligned Perturbation Taxonomy}
\label{sec:taxonomy}

\ToolRobustBench{} defines four single-family perturbation families aligned with these axes.

\textbf{Tool-interface perturbation} applies interface-level shifts, including surface changes to tool names, abstracted descriptions, and blurred boundaries among similar tools. It tests whether models rely excessively on lexical or descriptive cues.

\textbf{User-intent perturbation} varies the expression of the request through indirectness, underspecification, distracting context, and internal conflict. It tests whether models can recover the task goal and required arguments from natural-language input.

\textbf{Tool-output/observation perturbation} modifies returned content after the initial call. The model must recover the clean target from noisy feedback, distinguish the primary result from supporting evidence, and manage missing or conflicting evidence.

\textbf{Runtime-environment perturbation} enters during execution or the resulting runtime feedback. \emph{Runtime feedback} is the returned execution-state evidence made visible to the model; \emph{status} is its success, partial-success, or error state; \emph{failure type} categorizes an unsuccessful state; and \emph{final result} is the output that should be retained after interpreting all feedback. \emph{Retryability} denotes whether a failed or partial execution should be retried under the observed runtime state. For example, a timeout or temporary service unavailability may be retryable, whereas a permission denial or invalid argument error is usually non-retryable.

The 14 subtype identifiers used in the results are defined as follows: A1 name shift, A2 description abstraction, A3 sibling confusability; B1 indirectness, B2 underspecification, B3 distraction, B4 conflict; C1 structure noise, C2 evidence loss, C3 value corruption, C4 evidence competition; and D1 availability failure, D2 runtime variability, D3 feedback quality. Thus, for example, ``C2'' always denotes missing returned evidence rather than a generic severity level. At the template level, a deterministic rule derives each perturbed instance from a clean seed. Appendix Table~\ref{tab:subtype-details} specifies the altered input field, construction operation, and intended diagnostic target for every subtype.

\subsection{Cascade-Aware Error Attribution}

Errors can cascade: a final incorrect argument may originate in S1/S2 tool misselection, and a runtime symptom may follow from upstream argument corruption. The scorer therefore records the observed and primary errors, earliest failed and source stages, and cascade and boundary-violation indicators (Table~\ref{tab:diagnostic-fields}). It derives the observed label through a fixed order---call presence, format validity, tool resolution and match, required arguments, values, then execution/post-execution success---and traces downstream labels to the earliest compatible source. A boundary violation is flagged when the source lies outside the intended perturbation family and its permitted downstream consequences. No LLM judge is used.

\subsection{Metrics}

Using the instance-level indicator $s_i$ defined in Section~\ref{sec:task-formulation}, model $m$'s success on a set $\mathcal{D}$ is
\begin{align}
\mathrm{Succ}_m(\mathcal{D}) &=
\frac{1}{|\mathcal{D}|}\sum_{i\in \mathcal{D}}s_i.
\end{align}
Let $\mathcal{D}_{clean}$ be clean instances, $\mathcal{D}_{f,z}$ be instances in family $f\in\{A,B,C,D\}$ at severity $z$, and $Z=\{\text{light},\text{medium},\text{heavy}\}$. We report
\begin{align}
\mathrm{Clean}(m) &= \mathrm{Succ}_m(\mathcal{D}_{clean}), \\
\mathrm{Robust}_{f}(m) &= \frac{1}{3}\sum_{z\in Z}
\mathrm{Succ}_m(\mathcal{D}_{f,z}), \\
\mathrm{Overall}(m) &=
\frac{1}{4}\sum_{f\in\{A,B,C,D\}}\mathrm{Robust}_{f}(m), \\
\mathrm{Drop}_{f}(m) &=
\mathrm{Clean}(m)-\mathrm{Robust}_{f}(m).
\end{align}

For failed instances $\mathcal{F}_{f}$, let $e_i^{o}$ and $e_i^{p}$ be the observed and primary error labels and let $b_i$ indicate a boundary violation. The cascade rate (CR) and boundary-violation rate (BVR) are
\begin{align}
\mathrm{CR}_{f} &=
\frac{1}{|\mathcal{F}_{f}|}\sum_{i\in\mathcal{F}_{f}}
\mathbf{1}[e_i^{o}\neq e_i^{p}], \\
\mathrm{BVR}_{f} &=
\frac{1}{|\mathcal{F}_{f}|}\sum_{i\in\mathcal{F}_{f}}
\mathbf{1}[b_i=1].
\end{align}
where $\mathbf{1}[\cdot]$ is the indicator function.
The primary-error distribution counts attributed source failures rather than downstream symptoms.

For a mixed-family pair $q=(f_1,f_2)$ at severity $z$, let $M(m,q,z)$ denote mixed-instance success, $W(m,q,z)$ the weaker constituent success, and $\bar{S}(m,q,z)$ their mean. Mixed records are matched to both isolated constituents by model, source anchor, severity, and constituent subtype before aggregation. We report
\begin{align}
\Delta_{W}(m,q,z) &= M(m,q,z)-W(m,q,z), \\
\Delta_{\mathrm{mean}}(m,q,z) &= M(m,q,z)-\bar{S}(m,q,z).
\end{align}
Figure~\ref{fig:cross-vs-single} reports contrasts with both $W$ and $\bar{S}$.
A positive $\Delta_W$ means only that the mixed condition exceeds the lower isolated score; it can coexist with a negative $\Delta_{\mathrm{mean}}$ when the other constituent is much easier. Thus, $\Delta_W$ detects interaction around the harder constituent, whereas $\Delta_{\mathrm{mean}}$ measures the overall loss from isolated performance.

For single-family uncertainty, we use 20,000 paired percentile-bootstrap replicates with fixed seed 20261002. The main resampling unit is the 48 clean source anchors; a tool-cluster bootstrap sensitivity analysis resamples the 16 tools as whole clusters, preserving all three anchors and repeated perturbations within a tool. Mixed-family intervals resample their 16 source anchors as whole clusters. Leave-one-tool-out and leave-one-anchor-out analyses test whether aggregate conclusions depend on a single tool or anchor.

\section{Experimental Setup}

\subsection{Data Construction}
\label{sec:data-construction}

\ToolRobustBench{} is built through a four-step construction pipeline. First, we define 40 deterministic local tools in 12 functional groups; every tool has a hand-written schema, parameter constraints, executor, and output format. Second, we instantiate natural-language requests with concrete arguments and execute their gold calls. Tasks that resolve to the expected result become clean anchors. Third, we sample 16 tools with seed 20260511 and derive stage-aligned variants: A/B inherit the clean call and result, C alters returned evidence while retaining the target, and D alters the expected runtime status, retryability, failure type, or result. Fourth, a construction check verifies that each template modifies its designated input field and that light, medium, and heavy variants apply progressively stronger operator sets before serializing the gold and diagnostic fields. Language-model assistance contributes candidate-template wording; deterministic code generates every evaluated instance, label, and score. Appendix~\ref{app:data-construction}, Appendix Table~\ref{tab:clean-seed-example}, and Appendix Table~\ref{tab:subtype-details} document the environment, a complete anchor, and subtype operations.

\paragraph{Severity-controlled expansion.}
Each clean anchor is crossed with deterministic family--subtype--severity operators, producing paired conditions that differ at the target stage. A template is retained only when it changes the designated field, produces a nontrivial light condition, and applies progressively stronger transformations from light to heavy. Light uses a weak primary operator, medium strengthens or amplifies it, and heavy uses the strongest controlled composition while retaining a defined target. The resulting severity levels form a reproducible input-side stress axis; Appendix Table~\ref{tab:severity-criteria} gives the criteria.

\paragraph{Diagnostic label construction.}
Instances store the gold and attribution targets defined above, plus runtime-decision targets where applicable; Appendix Table~\ref{tab:construction-labels} maps them to serialized fields.

\paragraph{Dataset scale.}
The complete construction space contains 40 deterministic tools in 12 groups; the main experiment uses 16 sampled tools, four perturbation families, 14 subtypes, and conditions \{clean, light, medium, heavy\}. Each of the seven models contributes 48 seed tasks for each of four family-specific clean baselines and $48 \times 14 \times 3$ perturbed records. Thus,
\[
7 \times \left[(4 \times 48) + (14 \times 3 \times 48)\right] = 15{,}456
\]
single-family raw model-output records, comprising 1,344 stored clean-baseline records and 14,112 perturbed records. Mixed-family records form a separate exactly matched evaluation set.

\subsection{Data Quality and Scorer Reliability}

We audit 140 stratified single-family records while hiding scorer labels during annotation. Across core task, attribution, and runtime labels, human--scorer agreement is 0.814--0.957 (Cohen's $\kappa=0.734$--0.873), providing an external reliability check on the deterministic scorer. Appendix~\ref{app:validity} and Appendix Table~\ref{tab:integrated-validation} give the full protocol and label-level results.

\subsection{Models and Data Allocation}

We evaluate 7 models on the shared task set and sampled registry. Per model, A and D contain 480 records each because they have three subtypes, whereas B and C contain 624 each because they have four; every family additionally stores its own 48-record clean baseline. These family-specific baselines support paired within-family comparisons and explain the four clean copies in the 15,456-record accounting above.

\subsection{Scoring Workflow}

Scoring follows the pre- and post-execution protocol in Section~\ref{sec:task-formulation}. All providers receive identical task content and scoring criteria; provider-specific wrappers handle request serialization. Appendix~\ref{app:validity} describes scorer normalization and compatibility checks.

\section{Single-Family Results}

\subsection{Overall Robustness and Family Ranking}

\noindent\textbf{Finding 1: Strong clean tool-calling performance masks a large stage-wise robustness gap.}
Table~\ref{tab:leaderboard} gives the final model ranking. \texttt{claude-sonnet-4-6} ranks first at 0.766 overall robustness, followed by \texttt{deepseek-v4-pro} at 0.749 and \texttt{gpt-5.4-mini} at 0.712. Average clean success is 0.979, with three models at 1.000, while perturbed robustness ranges from 0.664 to 0.766. An average paired drop of 0.271 establishes a marked separation between clean capability and perturbation robustness.

\noindent\textbf{Finding 2: Tool-output/observation perturbation is the dominant bottleneck across all evaluated models.}
Family-level results identify where this separation arises. Averaged across models, tool-interface perturbation is least damaging at 0.918, followed by user-intent perturbation at 0.773 and runtime-environment perturbation at 0.688. Tool-output/observation perturbation is the bottleneck at 0.455, and no model reaches 0.60 in this family. Across the seven evaluated models, tool selection and grounding are more reliable than recovery from corrupted or incomplete returned evidence.

\subsection{Subtype and Severity Effects}

\noindent\textbf{Finding 3: Missing or competing returned evidence is substantially harder than surface-level interface change.}
Average success falls from 0.979 in clean conditions to 0.869, 0.724, and 0.491 under light, medium, and heavy perturbations, respectively. Conservative tool-cluster 95\% intervals are 0.857--0.880, 0.698--0.752, and 0.446--0.537, exposing failures largely hidden in clean evaluation.

Subtype results explain much of the family-level difference. C2 Return Evidence Loss is the hardest subtype (0.142), followed by C1 Return Structure Noise (0.460) and D2 Runtime Variability (0.469), whereas A2 Description Abstraction and A1 Name Surface Shift remain high at 0.927 and 0.930. Within families B and D, B3 Distraction and D2 Runtime Variability are the hardest subtypes, indicating sensitivity to competing context and unstable execution feedback.

\subsection{Recoverability of Evidence-Loss Perturbations}

C2 Return Evidence Loss is the hardest subtype, so we additionally audit whether its fixed gold targets can be reconstructed from the perturbed information visible to the model. As a machine witness, we count an instance when at least one of the seven evaluated models succeeds under the exact-match scorer. Among 144 C2 instances, 49 have such a witness: 23/48 light, 25/48 medium, and 1/48 heavy, for 34.0\% overall (Wilson 95\% CI 26.8--42.1).

In a blinded study spanning all 16 tools, two domain annotators, each with two years of experience in LLM tool-use evaluation and data annotation, independently achieved exact recovery on 14/60 and 19/60 perturbed prompts. Their binary exact/non-exact outcomes agree on 55/60 ($\kappa=0.793$). Together, the machine and human results establish a nontrivial exactly recoverable subset under strict matching. Appendix Table~\ref{tab:c2-recoverability} reports the full severity breakdown and uncertainty.

\subsection{Failure Taxonomy and Cascade Attribution}

\noindent\textbf{Finding 4: Cascade-aware attribution separates downstream symptoms from upstream failure sources.}
Across perturbed failures, \emph{incorrect argument} is the dominant primary error, followed by \emph{tool misselection} and \emph{runtime failure}; outright no-calls and schema-format violations are comparatively rare. Family composition is strongly concentrated: 89.1\% of tool-interface failures and 89.9\% of user-intent failures are tool misselections, 91.7\% of tool-output/observation failures are incorrect arguments, and 97.6\% of runtime-environment failures are runtime failures. An aggregate failure rate would collapse these distinct diagnostic modes.

\begin{figure}[t]
    \centering
    \includegraphics[width=\linewidth]{picture/fig04_failure_taxonomy.png}
    \caption{Primary failure taxonomy by perturbation family. Family-specific failure compositions show why aggregate success should be interpreted together with attribution.}
    \label{fig:failure-taxonomy}
\end{figure}

Cascade-aware attribution sharpens this interpretation. Runtime-environment perturbation has the highest cascade rate, 0.638, because runtime feedback occurs late in the tool chain and can expose upstream selection or argument errors. Tool-interface perturbation has a cascade rate of 0.352, often because boundary confusion produces downstream argument or execution symptoms. Tool-output/observation perturbation has a cascade rate of 0.003, indicating that its failures usually arise directly during evidence selection or result recovery. The 0.006 boundary-violation rate for runtime-environment perturbation confirms that the high cascade rate reflects valid upstream propagation (Appendix Table~\ref{tab:boundary-stats}).

\noindent\textbf{Targeted repair audit.}
To test whether cascade-aware labels identify actionable targets, we intervene structurally at the attributed source stage. The source-matched repair clears all failure flags in 71/98 records (72.4\%), including 48/48 single-primary and 23/28 downstream-only Tier-2 cases (82.1\%). In the latter group, every remaining recorded failure lies after the attributed source stage, so correcting that source removes the associated downstream symptoms and converts an end-to-end failure into a stage-specific repair target (Appendix Table~\ref{tab:counterfactual-attribution}).

\subsection{Post-Execution Diagnostics}

Runtime-environment instances require a post-execution decision about status, retryability, failure type, and final result, as defined in Section~\ref{sec:taxonomy}. Averaged across models, matching is highest for retryability (0.949), followed by failure type (0.917), status (0.783), and result (0.738). Models therefore identify many explicit runtime labels but are less reliable at recovering the final result from mixed feedback. Appendix Figures~\ref{fig:app-stage2} and \ref{fig:app-gemini-profile} provide detailed profiles.

\section{Mixed-Family Results}
\label{sec:mixed}

We screen the broader pairwise space and select five non-degenerate pairs with pronounced effects, interpretable mechanisms, and non-saturated model differences: A2+B3, A3+C4, A1+D1, B4+C4, and B2+D2. They cover abstraction--distraction, sibling ambiguity--evidence competition, name shift--availability failure, intent conflict--evidence competition, and underspecification--runtime variability. Each model--pair--severity cell has 16 matched instances (70 cells total); Appendix Figure~\ref{fig:app-gpt-cross-matrix} retains the broader screen.

\noindent\textbf{Finding 5: Mixed-family conditions are substantially harder than the mean of their exactly matched isolated constituents.}
At medium severity, mixed success is 0.448 versus 0.520 for the weaker constituent and 0.719 for the constituent mean: gaps of $-0.071$ (source-anchor bootstrap 95\% CI $-0.109$ to $-0.023$) and $-0.271$ ($-0.296$ to $-0.246$). At heavy severity, mixed success is 0.200 versus a constituent mean of 0.519, a gap of $-0.319$ ($-0.363$ to $-0.274$). Across both severities, mixed success is 0.295 below the constituent mean ($-0.319$ to $-0.271$).

The largest mean-constituent gap is A3+C4: sibling ambiguity induces upstream wrong-tool choices, then competing evidence removes the downstream correction signal (79/112 medium and 102/112 heavy primary wrong-tool failures). B4+C4 makes request and evidence conflicts support different interpretations; B2+D2 combines missing intent slots with inconsistent attempts. A1+D1 is milder because explicit unavailability remains a stable decision cue.

\noindent\textbf{Finding 6: Local positive contrasts arise when composition changes which cues the model trusts.}
A2+B3-heavy scores 0.304: above B3 alone at 0.214 ($\Delta_W=+0.089$), but below A2 alone at 0.955 and their mean of 0.585 ($\Delta_{\mathrm{mean}}=-0.281$). Thus the positive sign denotes partial recovery from the harder constituent, not an overall gain. Its 17-to-7 transition balance concentrates among sibling retrieval tools: abstraction weakens B3's lexical shortcut and shifts attention to schemas, arguments, and scope. B2+D2-medium similarly scores 0.455 versus 0.429 for D2 ($\Delta_W=+0.027$), yet remains below B2 at 0.929 and their mean of 0.679 ($\Delta_{\mathrm{mean}}=-0.223$). Its 17-to-14 balance is concentrated in \texttt{deepseek-v4-flash}, where added ambiguity prompts cautious \texttt{partial}/retryable judgments instead of collapsing conflicting attempts into terminal states. The paired transitions support a cue-salience mechanism: conspicuous inconsistency triggers verification, whereas subtle inconsistency is more readily accepted (Appendix Figure~\ref{fig:app-nonmonotonic}; Table~\ref{tab:positive-mixed-audit}).

\section{Discussion}

The leaderboard ranks systems under a shared stress protocol, while family and source-stage scores identify why their performance differs. The strongest system reaches 0.766 overall, yet every model is weakest on returned-evidence handling, making observation recovery the shared engineering priority.

Diagnostic outputs map directly to interventions: clearer registry boundaries for interface failures, stronger constraint extraction for intent failures, provenance-aware verification for observation failures, and explicit status/retry semantics for runtime failures. Human reconstruction confirms a strictly recoverable C2 subset; source-stage repair clears 23/28 downstream-only Tier-2 cases; matched mixed conditions expose cross-stage effects hidden by isolated scores.

\section{Conclusion}

\ToolRobustBench{} evaluates tool-calling capability with deterministic, stage-aligned perturbations and cascade attribution. Across 15,456 single-family records, \texttt{claude-sonnet-4-6} ranks first at 0.766 overall, while every model is weakest under tool-output/observation perturbations. Recoverability, scorer, sensitivity, and targeted-repair audits support the stage-level results. Exactly matched mixed conditions show that isolated constituent means overestimate combined robustness and reveal cue-driven local reversals. The benchmark therefore reports both which models are most robust and which tool-use stage should be improved.

\section{Limitations}

\ToolRobustBench{} defines a controlled evaluation boundary: deterministic single-call tasks, four stage-aligned perturbation families, 14 single-family subtypes, and five exactly matched mixed-family pairs. Its reported scores characterize model behavior within this protocol. Live APIs, persistent state, long-horizon planning, and broader tool compositions are complementary evaluation settings. The released construction, scoring, audit, and analysis pipeline supports direct extension to those settings while preserving the same stage-level measurements.

\section{Ethical Considerations}

The benchmark uses synthetic requests, deterministic local tools, and model-generated outputs; it contains no personal or sensitive user data. Human review is limited to synthetic records, and annotators are not shown private gold files during blinded reconstruction. Outputs are used for robustness diagnosis rather than decisions about individuals.

\paragraph{Data and code.} An anonymized artifact containing construction code, records, scorers, analyses, and annotation materials is available at \url{https://anonymous.4open.science/r/toolrobustbench/}. It separates public annotation sheets from private gold keys and includes fixed seeds and manifests.

\paragraph{Language-model assistance.} Language models assisted candidate-template diversification and manuscript editing. Accepted templates and all evaluated instances, perturbations, executor outputs, and scorer labels were generated or checked deterministically; all claims remain the authors' responsibility.
